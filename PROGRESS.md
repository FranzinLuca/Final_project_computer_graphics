## 3. Architecture

### D1 — Three.js rather than raw WebGL

Raw WebGL would mean hand-writing the scene graph, the matrix stack, the PBR
shaders and the shadow-map passes before any project-specific work started. The
course permits either. The graded requirements are about hierarchical modelling,
animation, lighting and textures — Three.js gives a scene graph and a physically
based material system so that effort goes into the mechanism and the
constraints rather than into re-deriving infrastructure.

*Rejected:* Babylon.js (no advantage for this project, less familiar);
raw WebGL (cost not repaid by any graded criterion).

### D2 — No build step

The project runs directly from source files over HTTP. What is in the
repository is exactly what executes in the browser, which makes the GitHub Pages
deployment trivially reproducible and makes the repository legible to an
examiner without a toolchain.

*Rejected:* Vite/Rollup. Faster development, but introduces a `dist/` that is
not the source, and a build that must be re-run before every deploy.

### D3 — Vendored libraries, no CDN

The course requires the repository to contain all source including libraries.
Libraries live in `/lib` as actual files. Verified by loading the page with the
network disconnected.

### D4 — Import map

`index.html` declares an import map mapping the bare specifier `three` to
`./lib/three/build/three.module.js` and the prefix `three/addons/` to
`./lib/three/addons/`.

Necessary because addons import from `'three'` themselves — `OrbitControls.js`
begins with `import { Controls, ... } from 'three'`. Without the map the only
options are editing vendored library source (maintaining a fork) or introducing
a bundler (contradicts D2).

All paths are relative (`./lib/...`), because GitHub Pages serves the project
from `/Final_project_computer_graphics/`, not from the domain root. A leading
slash would work on localhost and 404 on deploy.

**Gotcha recorded:** since r168, `three.module.js` re-exports from a sibling
`three.core.js`. Both files must be vendored. Copying only the first gives a
404 that presents as an import-map failure.

### D5 — The decoupling rule

`audio.js` never imports `rig.js`; `rig.js` never imports `audio.js`. They
communicate through `main.js` and through the event bus.

Consequences that actually paid off:

- The entire audio engine (phase 1) was built and tested from the browser
  console before any geometry existed.
- A pad flash looks identical whether it came from a mouse click, a key press
  or the sequencer, because none of them talks to the geometry — all three
  produce the same `pad:hit` event.
- Adding a fifth thing that reacts to a hit (light pulse, VU meter) means
  touching one file, not three.

### D6 — `main.js` owns all wiring

Modules publish intent; `main.js` decides what intent means. The mapping from
knob index to audio parameter exists in exactly one place. `interaction.js` has
no import of `audio.js` at all.

### D7 — The event bus

A minimal pub/sub in `events.js`. `Set` rather than array for listeners, so
double-subscription cannot double-fire and removal is O(1). `on()` returns an
unsubscribe closure. `emit()` wraps each listener in try/catch, because
`emit('frame')` runs 60 times a second and one throwing subscriber would
otherwise kill the render loop.

**Events in use:**

| Event | Emitted by | Payload |
|---|---|---|
| `started` | main.js | `{ ctx }` |
| `frame` | main.js | `{ dt, t }` |
| `pad:trigger` | interaction.js | `{ padId, velocity }` |
| `pad:hit` | audio.js | `{ padId, time, velocity, source, layer }` |
| `transport:step` | audio.js | `{ step, time }` |
| `transport:start` / `:stop` / `:bpm` | audio.js | — |
| `transport:toggle` | interaction.js | `{}` |
| `case:toggle` | interaction.js | `{}` |
| `case:moving` | hierarchy.js | `{ open }` |
| `knob:change` | interaction.js | `{ index, label, value }` |
| `layers:changed` | audio.js | `{ layers }` |
| `record:armed` / `record:hit` | audio.js | — |

### D8 — One shared tween group

`tweens.js` exports a single `Group`, updated once per frame from `main.js`,
rather than relying on tween.js's implicit global group. Makes it possible to
pause, clear or step every animation as a unit, and keeps that state visible
rather than hidden inside the library.

### D9 — Render loop ordering

```js
tweens.update(timeMs);   // advance state scalars
hierarchy.update();      // solve scalars -> joint transforms
audio.update();          // release due visual events
rig.update(dt);          // pad press / LED decay
controls.update();       // camera
bus.emit('frame', ...);  // everything else
renderer.render(...);    // draw last
```

Everything that mutates the scene runs before the scene is drawn, so a frame
always shows the current tick's state rather than the previous one's. Solving
the hierarchy before tweening would render one tick stale.

`setAnimationLoop` rather than raw `requestAnimationFrame`: Three handles
rescheduling, it is the WebXR-compatible path, and it supplies a
`DOMHighResTimeStamp` on the same clock as `performance.now()`, which is exactly
what tween.js expects — no conversion.

`Math.min(clock.getDelta(), 0.1)` clamps the timestep so a backgrounded tab does
not resume with a 30-second delta.

## 4. Boot and deployment

### D10 — Click-to-start overlay

Browsers create an `AudioContext` in the `suspended` state unless construction
happens inside a user gesture. For a drum machine, a grader opening the link and
hearing nothing is the worst possible failure. The overlay makes the first
gesture unavoidable and gives a guaranteed context in which to call `resume()`.

Built on day 1, not at the end, per the risk table.

### D11 — Deploy on day 1

GitHub Pages was enabled and an empty scene confirmed live before any feature
work. Repository-structure problems that break deployment are found on day 1
rather than day 22.

### D12 — Diagnostics readout

A fixed corner element showing fps, draw calls, WebGL version and audio context
state. Present so that "does it run on the grader's machine" is answerable from
the deployed page rather than by guessing. To be kept — it costs one DOM write
every half second.

### D13 — Console handles on `window`

`Object.assign(window, { THREE, scene, camera, audio, rig, hierarchy, ... })`.
Deliberate during development; a global namespace dump in production.
**Action before submission:** delete or gate behind a `?debug` query parameter,
and record it in the report's known-limitations section if kept.

## 5. Audio engine

### D14 — Synthesis, not samples

All 16 voices are oscillators and filtered noise. No audio files. Removes all
licensing questions, keeps the repository small, and makes every sound
explainable as a node graph rather than as an asset someone else made.

### D15 — Parameterised voice constructors

Six recipe constructors (`makeKick`, `makeSnare`, `makeClap`, `makeHat`,
`makeCowbell`, `makeZap`) produce all 16 voices. The three toms are one recipe
with three sets of numbers, not three copies of a function. Retuning a family is
one edit.

### D16 — Fresh nodes per hit

`OscillatorNode` and `AudioBufferSourceNode` are single-use by specification:
once stopped they cannot restart. Every hit builds a small graph, schedules it
and lets it be garbage collected. This is the intended pattern, not a leak.

### D17 — Exponential envelopes with a non-zero floor

Perceived loudness is roughly logarithmic, so a linear fade sounds like it stops
abruptly. `exponentialRampToValueAtTime` cannot target zero — exponential decay
never reaches it and the API throws — so the floor is `0.0001`, about −80 dB and
inaudible.

### D18 — Lookahead scheduler

The core timing decision. `setTimeout`/`setInterval` are best-effort: they fire
when the main thread is free, and the main thread is also running the render
loop, the raycaster and OrbitControls. Scheduling each note from the previous
note's actual firing time compounds the error until the beat visibly slides.

Web Audio has its own clock, `ctx.currentTime`, on a separate high-priority
thread. Anything scheduled against it is sample-accurate regardless of main
thread load.

So the JS timer stops *playing* notes and starts *planning* them. A 25 ms
interval wakes up and commits every note falling in the next 100 ms to the audio
clock. The timer can jitter ±20 ms with no audible consequence, because it only
decides when to think, not when to sound.

Two constants and the trade-off between them:

- `LOOKAHEAD_MS = 25` — how often the planner wakes.
- `SCHEDULE_AHEAD = 0.1` — how far forward it commits. Larger is more robust
  against a stalled main thread, but delays the effect of a tempo or pattern
  change, because notes are already locked in.

Pattern: Chris Wilson, "A Tale of Two Clocks".

### D19 — Absolute step times, never accumulated

Every step sits at `startTime + n * secondsPerStep()`. The scheduler computes
each time from that formula rather than doing `nextTime += secondsPerStep`.
Accumulation would let floating-point error build up over a long session;
computing from an absolute anchor cannot drift. It also gives quantization a
single unambiguous reference.

### D20 — Tempo changes rebase `startTime`

Because step positions are derived from `startTime`, assigning a new BPM would
move every step, including ones already committed to the audio clock.
`setBpm` instead rebases `startTime` so the next scheduled step keeps the exact
time it was promised, and the new spacing applies from there. The beat does not
stumble when the tempo changes mid-loop.

### D21 — Quantization by rounding, with a guarded modulo

```
raw   = (t − startTime) / secondsPerStep
step  = ((round(raw) mod L) + L) mod L
```

**Round, not floor.** Flooring always drags a hit backwards, so a note played
10 ms early lands a full step late. Rounding snaps to the nearest step, which
matches how people play — most players rush.

**The modulo is written out** because JavaScript's `%` keeps the sign of the
left operand, so a hit arriving before `startTime` would produce a negative
index.

### D22 — Deferred visual events

The scheduler commits notes up to 100 ms early. Emitting `pad:hit` at schedule
time would flash the LEDs before the sound arrives. Instead, scheduled events go
into a queue stamped with their audio time, and `audio.update()` — called once
per rendered frame — releases them when `ctx.currentTime` catches up. Sound and
light land together.

Live hits are emitted immediately, since their audio time is *now*.

### D23 — Layer routing; live hits bypass the layers

```
scheduled hit -> layer[i].output --\
                                    >-- master -> masterFilter -> destination
live hit --------------------------/
```

Pressing a pad is always audible even if the layer being recorded into is
muted — otherwise arming a muted layer would appear broken.

### D24 — Master bus before the destination

Nothing connects to `ctx.destination` directly. One place for overall volume,
and one place for phase 5's `AnalyserNode` to tap. Had voices connected straight
to the destination, the analyser would have nothing to observe and a bus would
have to be retrofitted into working code.

The filter sits *after* the master gain so the analyser sees what actually
reaches the speakers — closing the filter should visibly dim the lights.

### D25 — Solo is exclusive by implication

If any layer is soloed, only soloed layers are audible and mute is irrelevant.
Hardware convention, and it avoids the confusing state of a track that is both
soloed and muted.

### D26 — Parameter changes ramp

`setTargetAtTime` rather than assigning `.value`. An instantaneous gain change
is a step discontinuity in the waveform, which is audible as a click. ~30 ms
time constant: immediate to the hand, silent to the ear.

### D27 — Exponential filter mapping

`f(t) = 140 · (18000/140)^t`. Pitch perception is logarithmic — 140→280 Hz is
one octave, the same musical distance as 9k→18k. A linear map would spend the
bottom 1% of knob travel on everything audible and the rest on almost nothing.
Measured: 0 → 140 Hz, 0.25 → 471, 0.5 → 1587, 0.75 → 5345, 1.0 → 18000.

### D28 — Hi-hat choke group

A closed hat cuts off a ringing open hat, as a real hi-hat does — both sounds
come from one pair of cymbals and cannot physically overlap. Implemented by
holding the ringing voice's output gain node per choke group and ramping it
down over 20 ms.

Uses `cancelAndHoldAtTime` where available, because it freezes the envelope at
its value *at the choke time* rather than its value now — and the choke time may
be up to `SCHEDULE_AHEAD` in the future. Falls back to
`cancelScheduledValues` + `setValueAtTime`.

### D29 — One hit per pad per step

Recording deduplicates: hitting the same pad twice inside one sixteenth is a
double-trigger, not two notes.

### D30 — Pattern data shape

```js
{ length: 16, steps: [ [ { padId, velocity } ], ... ] }
```

Plain JSON, no classes. A recorded pattern and an authored preset are the same
shape, so phase 7's presets need no conversion layer, and `exportPatterns()` is
a `JSON.parse(JSON.stringify(...))`.

## 6. Geometry and the hierarchy

### D31 — `rig.js` builds, `hierarchy.js` moves

The project plan put the joint chain in `hierarchy.js` at phase 4. Building the
skeleton in `rig.js` at phase 2 and having phase 4 supply only the motion
avoided demolishing and rebuilding the parent–child tree.

The constraint solver `applyPose` was then moved *out* of `rig.js` into
`hierarchy.js` at phase 4, leaving `rig.js` as pure construction. This buys a
statement that can be made in one sentence:

> Exactly one function in this project writes to a joint transform.

Everything else moves a scalar and lets the constraint propagate. Transforms are
a pure function of state, recomputed every frame, so they cannot drift out of
sync with it.

*Deviation from the plan, recorded deliberately.*

### D32 — Hinges are empty Groups on the axis of rotation

The single most important habit in the whole hierarchy. Three.js rotates an
object about its own origin, and a `BoxGeometry`'s origin is its centre — so
rotating a lid mesh directly spins it about its middle like a propeller. Every
hinge is an empty `Group` placed exactly on the hinge line, with the mesh offset
by half its length inside it. The group is the hinge; the mesh hangs off it.

Get this wrong and no amount of animation tuning fixes it.

### D33 — The joint chain

```
caseBody
├── lidPivot            hinge, rotation.x   0 → −110°
├── wingLeftPivot       hinge, rotation.z   0 → −95°
├── wingRightPivot      hinge, rotation.z   0 → +95°
├── scissor
│   ├── armPivotsA ×2   rotation.z  +θ,  position.y = h/2
│   ├── armPivotsB ×2   rotation.z  −θ,  position.y = h/2
│   └── deck            position.y  = h(θ)
│       └── padGrid
│           └── pad ×16
└── linkagePivot        rotation.x
    └── controlPanel    counter-rotated
        └── knob ×6
```

Five to six levels deep with three branches, and every level carries a real
degree of freedom rather than being a decorative sub-mesh.

The entire configuration of the mechanism is **four numbers**:
`{ lid, wing, theta, linkage }`.

### D34 — The scissor constraint

Two arms of length `2·armHalf` pinned at their midpoints, one end of each on the
base and the other under the deck. Each arm makes angle θ with the horizontal,
so the rise from base pin to cross pin is `armHalf·sin θ`, and the rise from
cross pin to deck is the same again:

```
h(θ) = 2 · armHalf · sin(θ)
```

**θ is the only thing animated.** Deck height is derived through the constraint;
the cross pin sits at `h/2` by the same derivation; the pad grid rises without a
line of code of its own because it is a child of the deck.

This is the difference between animation that *exploits* hierarchical structure
and animation that merely coexists with it — the alternative is keyframing each
part separately and hoping they agree.

Two arm pairs, front and back, share θ. They read as a mechanism with width
rather than a flat linkage, and are driven from one value.

### D35 — Counter-rotation of the control panel

```
panel.rotation.x = −linkage.rotation.x + PANEL_TILT
```

The panel is a child of an arm that pitches as the case opens. Left alone the
knobs would face the ceiling. Negating the parent's rotation cancels it exactly;
`PANEL_TILT` (12°) then sets the attitude actually wanted.

A constraint expressed *through* the hierarchy — a parent's rotation compensated
by a child's — rather than by detaching the panel into world space. The panel
still inherits the parent's *position*, so it rides up and back with the linkage
while keeping its own orientation.

### D36 — Staggered sequence, not one tween

One tween across all four joints reads as a rigid object scaling open. Delays
turn it into a sequence of mechanical events with implied causality: the lid
must clear before the lift has room, so the lift starts 500 ms in.

| Joint | Delay | Duration | Easing |
|---|---|---|---|
| lid | 0 | 900 ms | `Cubic.Out` |
| wings | 200 ms | 750 ms | `Quadratic.Out` |
| scissor θ | 500 ms | 1100 ms | `Back.Out` |
| panel linkage | 900 ms | 600 ms | `Cubic.Out` |

Each joint gets its own easing because they are different physics: the lid falls
back under gravity, the lift is motor-driven against it.

Folding reverses the order (panel stows first, lid closes last) and drops the
overshoot — a lift being lowered under control does not bounce.

### D37 — Overshoot verified against the constraint's monotonic region

`Back.Out` overshoots by 1.10 of its range. On a *sine-based* constraint this
needs checking: past 90° `sin` decreases, so an overshoot beyond 90° would make
the deck visibly stutter downward at the top of its travel.

Computed: θ peaks at **63.2°** against a 58° target. Deck reaches 0.526 before
settling at 0.511. Safely inside the monotonic region.

Recorded because "I checked that the easing overshoot stays inside the
monotonic region of the constraint" is a different claim from "it looked fine".

### D38 — Interruptible motion

Each tween starts from the joint's *current* value, not from the nominal pose,
and a new sequence stops the tweens in flight first. Pressing the toggle halfway
through an unfold reverses each joint from wherever it happens to be, with no
jump.

### D39 — Pad press by exponential decay, not per-hit tweens

A tween would have to be cancelled and restarted on every retrigger, and at
sixteenth notes that is constant allocation for an effect that is one float.
Exponential decay (`press *= exp(−dt·11)`) retriggers correctly for free:
setting `press` back to 1 mid-fall simply restarts it.

A case where the obvious tool was the wrong one.

### D40 — Auto-unfold on power-on

The case starts closed and unfolds 350 ms after the overlay is dismissed —
delayed so it starts after the fade rather than underneath it. Satisfies "case
unfolds on load or on command" and makes the mechanism the first thing seen.

## 7. Textures and materials

### D41 — Procedural generation, no image files

Every map is computed at load time from noise and filters. No licensing
questions, no binary assets in the repository, every parameter explainable.
`/assets` is consequently empty.

### D42 — Colour space is not optional

Base colour maps hold perceptual sRGB values and are tagged `SRGBColorSpace` so
the renderer linearises them before lighting. Normal and roughness maps hold raw
numbers — a normal map's RGB is a direction vector, not a colour — and stay
linear (`NoColorSpace`, the default).

Tagging a normal map as sRGB bends every surface normal slightly wrong. The
failure looks like "the lighting seems a bit flat" rather than anything
obviously broken, which is why it survives in projects for months.

### D43 — Normal maps derived from height fields

```
dx = h(x−1) − h(x+1)
dy = h(y−1) − h(y+1)
n  = normalise(dx·s, dy·s, 1)
packed = n · 0.5 + 0.5
```

The `+1` in Z keeps the normal pointing out of the surface: a flat region gives
`(0,0,1)`, which packs to `(0.5, 0.5, 1.0)` — the characteristic lavender of an
unperturbed normal map. Vectors run −1..1 but texture channels hold 0..1, hence
the packing; the shader applies the inverse.

Delivered as a `DataTexture` rather than a canvas, since it is a vector field
and never needs to be drawn.

### D44 — Wrap-around addressing in blur and normal generation

Neighbour lookups wrap rather than clamp. A clamped blur leaves a visible seam
where the texture repeats. Separable blur (two 1D passes) rather than a 2D
kernel: O(n) per pixel instead of O(n²).

### D45 — One height field drives three maps

For each material family the same field produces colour, normal and roughness.
A groove is therefore simultaneously darker, tilted and duller — which is what
makes it read as one physical surface rather than three overlaid effects.

### D46 — Anisotropy is the whole character of brushed metal

Blur white noise hard along one axis (radius 14) and barely at all across it
(radius 1). The streaks that survive read as directional brush grooves.
Rubber uses radius 1 in both directions for a tight isotropic stipple; wider
starts to read as leather.

### D47 — Material families so far

| Family | Base colour | Normal | Roughness / metalness | Emissive |
|---|---|---|---|---|
| Chassis (brushed metal) | procedural streaks | directional grooves | 0.44 / 0.92 | — |
| Shell (painted panel) | same maps, dark tint | same, half strength | 0.62 / 0.55 | — |
| Pads (rubber) | stipple tint | fine stipple | 0.88 / 0.0 | LED plate |
| Plastic (panel, knobs) | coarse grain | mild | 0.66 / 0.10 | — |

Floor and wall families are phase 6. Chassis and shell share maps with different
tint and finish — costs nothing and ties the family together visually.

### D48 — Per-pad LED material

The LED is a slightly oversized plate under the rubber cap, so a rim of colour
shows around the pad. Each pad needs its own material instance because
`emissiveIntensity` is animated independently — 16 material instances, which is
16 draw calls' worth of state but the only way to drive them separately without
a shader.

Hue per pad comes from `pads.js`, grouped by row: kicks/backbeat, toms, cymbals,
percussion.

## 8. Rendering and lighting (interim)

### D49 — ACES Filmic tone mapping

Three renders lighting in linear space where values exceed 1.0; tone mapping
compresses that into displayable range. ACES rolls off highlights rather than
clipping them to flat white. With phase 5's bass-driven lights pushing intensity
hard, this is the difference between a bloom-like falloff and an ugly blowout.

### D50 — Pixel ratio capped at 2

Fragment shading cost scales with the *square* of the pixel ratio. An uncapped
3× display does nine times the fragment work of a 1× one for a difference almost
nobody sees.

### D51 — Shadow camera sized to the scene

A directional light casts shadows through an orthographic camera. Too small and
shadows clip at the edges; too large and a 2048² depth map is spread over a huge
area and edges go blocky. Currently ±2.2 units.

`shadow.bias = −0.0006` and `normalBias = 0.012` fight shadow acne — the
self-shadowing stripes from depth-map precision. Too much bias and shadows
detach from their objects ("peter-panning"). Expect retuning in phase 5 when the
real lights arrive.

**Current lights are placeholders**: hemisphere ambient, a warm key with
shadows, a cool rim so chassis edges separate from the background. Phase 5
replaces them.

## 9. Interaction

### D52 — `event.code`, not `event.key`

`code` is the physical key position; `key` is the character that position
produces under the current layout. The mapping is spatial — a grid of keys onto
a grid of pads — so physical position is the thing actually meant. On AZERTY,
`KeyQ` sits where `A` is printed, and a `key`-based map would scatter the block.
Also sidesteps Shift entirely.

Map: `1 2 3 4 / Q W E R / A S D F / Z X C V` → pads 0–15, left-to-right,
top-to-bottom, matching both the grid layout and the `PADS` array order.

Commands: **Space** transport, **O** unfold/fold.

### D53 — Vertical drag for knobs, not circular

Circular drag is more skeuomorphic but worse: ambiguous near the centre of
rotation, needs the knob large on screen, and degrades at shallow viewing
angles — which these have, sitting on a tilted panel. Vertical drag is the DAW
convention.

220 px for full range, divided by 5 with Shift held. Knob turns through 270°,
as a real potentiometer does.

### D54 — Pointer capture during knob drags

A 220 px vertical drag from a knob near the viewport edge leaves the canvas.
`setPointerCapture` keeps the drag alive.

### D55 — Camera suppressed during a control gesture

`controls.enabled = false` on a pad or knob hit. OrbitControls checks `enabled`
at the top of its own move handler, so clearing it in our `pointerdown` stops
the orbit even though its own `pointerdown` has already run. Right mouse button
is untouched, so orbiting is still available over the rig.

### D56 — Flat pickable array

The scene graph is traversed once at init to build a flat array of leaf meshes
plus `mesh.id → target` maps, rather than recursing on every pointer move.
Raycasting uses world matrices, which the renderer refreshes each frame — so
picking works unchanged while the case is unfolding and a pad is riding up on
the lift.

### D57 — Velocity from pointer pressure where it means something

Pen and touch report real pressure; a mouse always reports 0.5 when held, which
carries no information. Mouse hits are therefore full velocity; pen and touch
map pressure to 0.35–1.0.

### D58 — Auto-repeat suppressed

`if (event.repeat) return` — otherwise holding a pad key machine-guns at the OS
repeat rate.

## 12. Known limitations

For §10 of the report. Being candid here reads as competence.

1. **Quantization and the lookahead window.** A hit that quantizes *forward*
   onto a step the scheduler has already committed does not sound on the current
   pass; it appears from the next loop. This is the direct cost of
   `SCHEDULE_AHEAD = 0.1`. The honest fix — shrinking the window — trades
   robustness against main-thread stalls for it.
2. **`setInterval` throttling in background tabs.** Browsers throttle timers in
   hidden tabs, which can starve the planner. The 100 ms window absorbs brief
   throttling but not aggressive throttling. The standard fix is to run the
   planner in a Web Worker, whose timers are throttled less.
3. **Muted layers emit no visual events.** `scheduleStep` skips layers with zero
   effective gain, so a muted layer's pads do not flash. Arguably correct, but
   it is a decision rather than an accident.
4. **`window` globals.** D13 — to be removed or gated before submission.
5. **Fixed pattern length.** 16 steps, one bar. Nothing in the maths assumes it,
   but nothing exposes it either.
6. **No polyphony limit.** Rapid triggering allocates node graphs without a
   voice cap. Not a problem at realistic play rates; would be under an automated
   stress test.
7. **Shadow acne parameters are scene-specific.** `bias` and `normalBias` are
   tuned to the current light position and will need revisiting in phase 5.

## 13. Questions to be ready for in the oral

With the short answers.

**Why an import map instead of relative paths?**
Because the addons import `'three'` themselves — the alternative is forking
vendored library source or adding a bundler. (D4)

**Why the click-to-start overlay?**
The browser autoplay policy creates the AudioContext suspended; without a
gesture the project is silent. (D10)

**Why an event bus instead of direct calls?**
It makes the audio/geometry decoupling enforceable rather than aspirational, and
it is what allowed the audio engine to be built and tested before any visuals
existed. (D5, D7)

**Why does `render` come last in the loop?**
Everything that mutates the scene runs first, so a frame shows the current
tick's state. (D9)

**Why does nothing connect to `ctx.destination` directly?**
The master bus is the single point for volume and the tap for the analyser.
(D24)

**Why does the deck rise when theta changes?**
Because deck height is not authored. `h(θ) = 2·armHalf·sin θ` is evaluated in
the solver, and the pad grid is a child of the deck so it inherits the motion.
(D34)

**Why round rather than floor when quantizing?**
Flooring always drags a hit backwards; a note played 10 ms early would land a
full step late. (D21)

**How do you know the easing overshoot is safe?**
`Back.Out` peaks at 1.10 of range, putting θ at 63.2° against a 58° target —
inside the monotonic region of sine, so the deck cannot dip. (D37)

**Why `event.code` and not `event.key`?**
The mapping is spatial, so physical key position is what is meant; `key` would
scatter the block on non-QWERTY layouts. (D52)

**Why is the filter knob exponential?**
Pitch perception is logarithmic; a linear map would waste most of the travel
above 9 kHz. (D27)
